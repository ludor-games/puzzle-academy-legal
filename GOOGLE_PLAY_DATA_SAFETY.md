# Google Play Data Safety mapping — Puzzle Academy Android test

Audit date: 2026-09-17 (supersedes the 2026-09-13 Appodeal audit); AppsFlyer rows updated 2026-10-11 for ludor-games/puzzle-academy#1497; Meta rows (Facebook SDK, Meta Install Referrer) added 2026-10-28 for ludor-games/puzzle-academy#2496  
Package: `com.ludor.puzzleacademy`

This is an implementation-backed worksheet for the Google Play Data Safety form, not a submission export. It covers the current Android test build on `ludor-games/puzzle-academy` `origin/main`, after Appodeal was replaced by **AppLovin MAX** (Google AdMob mediated) and **AppsFlyer** was added (ludor-games/puzzle-academy#1379). Google Play defines “collected” as data transmitted off device, including by SDKs. “Shared” below follows Google Play’s third-party transfer definition and its service-provider exceptions.

**Keys:** builds from `main` ship with an empty AppLovin SDK key, empty ad units and an empty AppsFlyer dev key. In that state MAX skips initialization and AppsFlyer never starts, so neither transmits anything. The form must still describe the build that will run **with** keys, which is what the rows below assume. If an earlier artifact on the Play track still contains Appodeal, the 2026-09-13 declarations also apply until it is no longer distributed (see verification item 6).

## Consent

AppLovin MAX’s Terms & Privacy Policy flow is enabled (`ProjectSettings/AppLovinInternalSettings.json`). In the EEA, UK and Switzerland it shows Google’s consent form (UMP, `com.google.android.ump:user-messaging-platform:4.0.0`) during MAX initialization, and a refusal limits ads to non-personalized. Since ludor-games/puzzle-academy#2405 a bounded consent step (`ConsentStep`) waits for that answer, and AppsFlyer, the Firebase consent-mode update (`FirebaseConsentService`, #1344) and the Meta deferred-deep-link fetch all start after it. AppsFlyer reads the resulting IAB TCF strings (`enableTCFDataCollection`). The Meta fetch runs only outside GDPR or with TCF Purpose 1. **One read ignores the answer:** AppsFlyer's Meta Install Referrer read happens after a refusal too, with the refusing TCF string; AppsFlyer has no switch for it alone. Consent does not change which data types are declared, since Play’s form describes collection that can occur, but it matters for the privacy policy and for the “optional” column if collection becomes consent-gated.

## Not collected by the audited build

No repository evidence was found for collection of name, phone number, postal address, contacts, photos/videos, audio recordings, files/documents, calendar data, health/fitness data, messages, web browsing history, search history, or precise location. Local game saves and locally scheduled notification IDs remain on device and do not count as off-device collection. Firebase Messaging is present as a transitive notification dependency, but no remote push registration or token handling was found in game code; current gameplay reminders are local notifications only.

## Manual verification before Play Console submission

1. Confirm the exact AppLovin SDK 13.6.4, Google AdMob adapter 25.4.0.0 (Google Mobile Ads SDK 25.4.0) and AppsFlyer Android SDK 6.18.1 Data Safety declarations on the vendors’ pages. AppLovin’s and AppsFlyer’s pages could not be read during this audit; the rows citing them are marked *verify*.
2. Confirm **Other app performance data** and **Crash logs** against AppLovin’s declaration, and drop or add rows to match.
3. **Settled 2026-10-13 (felipe-mata): AppsFlyer is a service provider.** The live form was read the same day and needed no change for #1497. Purchase history is already declared Collected + Shared (sharing purpose: Advertising or marketing). The device-derived ID is declared under **Device or other IDs**, and **User IDs** is not selected. **Re-read 2026-10-28 (maintainer, ludor-games/puzzle-academy#2496):** Approximate location, Device or other IDs and App interactions were already selected with the sharing purposes the rows above require, so Data safety needed no change for the Meta flows. The Advertising ID declaration lacked **Fraud prevention, security and compliance**, which was added that day; it now matches the form-level row above.
4. **Settled 2026-10-28:** IP-derived analytics (Firebase), ad and attribution geolocation is entered as **Approximate location → Collected and Shared**; no Android location permission data is collected.
5. Confirm the merged Android manifest of the submitted build carries `com.google.android.gms.permission.AD_ID` (added by the ads and attribution SDKs), matching the advertising-ID declaration above.
6. Reconcile this worksheet against every active artifact/version on the Play track: Google Play requires the form to cover the union of data practices across distributed versions, not only the newest source tree. An Appodeal build still on a track keeps BidMachine, Bidon and Sentry in scope.
7. Confirm the Facebook SDK rows against Meta's own Google Play data safety guidance for `facebook-core` 18.3.0 (not read for the 2026-10-28 update), in particular Diagnostics and Approximate location.
8. Check whether the GDPR message in AdMob → Privacy & messaging lists Meta among its ad partners. The Meta fetch relies on TCF Purpose 1 alone, and Meta is not an IAB TCF vendor, so if the message does not name Meta, the consent it records never mentions Meta.
